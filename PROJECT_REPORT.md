# Project Report — Team Task Dashboard

## 1. Overview

This capstone integrates every skill area from the internship into one application: a Team Task Dashboard that displays 16 static sample tasks (`data/tasks.json`) through KPI summary cards, an inline SVG bar chart, and a sortable/filterable data table — built as a responsive, accessible, performance-optimized vanilla JS application with no external frameworks or libraries.

## 2. Design Decisions

- **No framework, no charting library.** The entire app is plain HTML/CSS/JS. The bar chart is generated by a small function that writes inline SVG directly from the data — this keeps total page weight under 20 KB and removes any dependency on a CDN or build step.
- **KPIs vs. chart/table scope.** The four KPI cards (Total, Done, In Progress, Overdue) always reflect the *entire* dataset, giving an at-a-glance team snapshot. The chart and table, by contrast, reflect the *currently filtered* subset — so a manager can filter to "Overdue" and immediately see both the full-team overdue count (KPI) and exactly which overdue tasks they are (table), without the two views contradicting each other.
- **Fetch-with-fallback for data loading.** `fetch("data/tasks.json")` is the primary data path, matching the task's requirement to load from a static JSON file. However, opening an HTML file directly via `file://` causes Chrome/Edge to block `fetch()` of local files under CORS. Rather than forcing every evaluator to spin up a local server just to see the dashboard work, `app.js` catches that failure and falls back to an identical embedded copy of the same data, so the app renders correctly either way. This was verified explicitly (Section 5).
- **Debounced search.** The search input re-filters on a 150ms debounce rather than every keystroke, avoiding unnecessary re-renders during fast typing — a small but real performance consideration at the interaction level, not just on page load.

## 3. Accessibility Implementation

| Feature | Implementation |
|---|---|
| Skip link | First focusable element, jumps to `#main-content` |
| Semantic structure | `<header>`, `<main>`, `<section>` landmarks with `aria-label`/`aria-labelledby` throughout |
| Sortable table headers | Real `<button>` elements inside `<th>`; `aria-sort` updates to `ascending`/`descending`/`none` and is reset on every other column when one is activated |
| Live region | `<p role="status" aria-live="polite">` announces "Showing X of Y tasks" after every filter or sort action, without moving focus |
| Chart accessibility | SVG has `role="img"` and a dynamic `aria-label` summarizing every bar's value in text (e.g. "Design: 4, Development: 4…") — a screen reader user gets the same information a sighted user gets from the bars |
| Form labeling | Every filter input has a bound `<label for=...>` |
| Keyboard operability | All controls are native `<button>`, `<select>`, or `<input>` elements — no custom-widget keyboard handling was needed, and this was verified in testing (Section 5) |
| Focus visibility | Global `3px` high-contrast `:focus-visible` outline |
| Reduced motion | `prefers-reduced-motion` respected |

## 4. Performance Optimizations

| Technique | Applied |
|---|---|
| No external libraries/fonts | Zero third-party network requests; system font stack |
| Minification | CSS 5,171 → 4,259 bytes; JS 11,829 → 8,325 bytes |
| Deferred script | `<script defer>`, placed at end of `<body>` |
| Debounced input | Search re-filters at most once per 150ms, not per keystroke |
| No layout-shifting assets | No images on the page at all — only CSS-drawn cards and inline SVG, so there is nothing to cause CLS |
| Lightweight charting | Hand-written ~15-line SVG generator instead of a charting library |

### What these results confirm

- **Data loading works in both scenarios** that a real evaluator might use: double-clicking the file directly (fallback path) and running a local server (real fetch path) — both produce an identical, correct 16-task dashboard.
- **All three filter types work correctly** and in combination: free-text search narrowed 16 tasks to the 1 matching "checkout"; the status filter correctly isolated exactly the 3 tasks marked "Overdue" in the source data.
- **Sorting is fully keyboard-operable**: focusing the "Task" column header and pressing Enter (not clicking) triggered the sort and correctly updated `aria-sort`, with no mouse involved.
- **Tab order is logical**: moving forward from the search box visits status, category, and reset, in reading order, with no keyboard traps.
- **The live region updates correctly**, giving screen reader users the same "Showing X of Y" feedback sighted users get visually from the shrinking table.
- **The chart's accessible name is generated dynamically from the same data driving the visual bars**, so it can never drift out of sync with what's on screen.
- **The responsive grid genuinely recomputes at mobile width** (verified via `getComputedStyle`, not just visual inspection) — 4 KPI columns become 2.

## 6. Challenges Encountered

- **`file://` CORS blocking `fetch()`** was the main technical challenge. Rather than documenting it as a known limitation, it was solved directly with the fetch-with-fallback pattern described in Section 2, and both code paths were independently tested in Section 5.
- **Keeping the chart accessible without a library** required building the `aria-label` text in parallel with the SVG bars, from the same counts array, so the two representations can't fall out of sync — a deliberate design choice over hard-coding a separate description.
- **No internet access** in this environment meant no CDN-hosted charting or UI library could be used even if desired — this constraint was treated as a performance feature rather than a limitation, since it kept the entire app dependency-free and under 20 KB.
