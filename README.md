# Team Task Dashboard — Week 5 Capstone

A mini web application integrating everything from Weeks 2–4: an interactive, accessible, responsive, and performance-optimized dashboard built with vanilla HTML, CSS, and JavaScript — no frameworks, no external libraries.

## Folder structure

```
week5-project/
├── index.html              the dashboard page
├── css/
│   ├── styles.source.css   readable source
│   └── styles.min.css      minified (referenced by index.html)
├── js/
│   ├── app.source.js       readable source
│   └── app.min.js          minified (referenced by index.html)
├── data/
│   └── tasks.json          the static JSON data file (16 sample tasks)
├── test/
│   └── automated-test.js   Playwright script: interactivity, keyboard, a11y, responsiveness
├── PROJECT_REPORT.md       full design/accessibility/performance writeup
└── README.md               this file
```

## Features

- **Dynamic data display:** 16 tasks loaded from `data/tasks.json`, rendered into KPI summary cards, a bar chart, and a sortable/filterable table.
- **Interactivity:** live search (debounced), status/category filters, click-to-sort table columns, reset button — all vanilla JS, no libraries.
- **Responsive design:** 4-column KPI grid → 2-column at narrow widths; chart+filters side-by-side → stacked; table scrolls horizontally on small screens.
- **Accessibility:** semantic landmarks, a skip link, `aria-sort` on sortable columns, an `aria-live` region announcing result counts, a labeled chart (`role="img"` + `aria-label`), full keyboard operability, visible focus states.
- **Performance:** zero external libraries or fonts, minified CSS/JS, deferred script, debounced search input, graceful fetch-with-fallback so the app works even opened directly via `file://`.

## Running it

**Option A — open directly:** double-click `index.html`. Since `fetch()` of a local JSON file is blocked by CORS when opened via `file://` in Chrome/Edge, the app automatically falls back to an identical embedded copy of the data — you'll see the exact same dashboard either way.

**Option B — run on a local server (recommended, uses the real JSON file):**
```bash
python3 -m http.server 8000
# then open http://localhost:8000
```

## Running the automated tests

```bash
npm install playwright
npx playwright install chromium
node test/automated-test.js
```

This verifies, against the real rendered page: KPI accuracy, search/status/category filtering, keyboard-operated sorting, logical tab order, the reset button, chart accessibility labeling, and the responsive grid at mobile width. See `PROJECT_REPORT.md` for the actual output.

## Design decisions

- **KPIs always reflect the full dataset**, while the chart and table reflect the active filters — so you always have an at-a-glance team snapshot even while drilling into a subset.
- **No charting library:** the bar chart is plain inline SVG generated by a ~15-line function, keeping the whole app dependency-free and under 20 KB total.
- **Fetch-with-fallback:** rather than requiring a local server (a common point of confusion for anyone just double-clicking a zip's files), the app detects the blocked fetch and transparently falls back to working sample data.
